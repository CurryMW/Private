# 百度 AI 情报与 GitHub 趋势推送 Issue Spec

## 本地验收状态（2026-09-20）

01—07 代码已本地集成；08 清理保留在工作区，不提交、不推送。当前离线测试通过不代表全部规格验收通过：真实 AI dry-run 仅返回空结果；GitHub 首次基线 dry-run 因搜索快照不完整而安全失败。生产任务未启用。以下条款仍为验收目标，不因记录差异而放宽。按订阅者明确许可，dry-run 可更新独立的搜索用量账本，但不写日报成功状态。

## Problem Statement

作为固定钉钉群的订阅者，我目前收到的 AI 技术日报依赖多个直接内容采集器，内容发现范围、失败行为和模型供应商都不再符合当前需求。现有系统还缺少一个能够按近期增长而非累计 Star 发现 AI 开源项目的独立报告；同时，模型地址和名称散落在配置与工作流中，无法安全切换到当前选定的模型服务。

我希望每天收到少量、可信、可追溯的中文 AI 情报，而不是为了保证“每天有消息”而收到旧内容或状态占位消息。我还希望每 72 小时收到一次真正反映近期增长的 GitHub AI 趋势报告，并且所有搜索与模型成本都有明确上限。

## Solution

将系统重构为两个相互独立的报告流程：`AI 情报摘要`只通过百度官方搜索 API 发现百度可检索到的中英文 AI 公开信息，在本地完成时间、站点、重复事件和证据过滤后，由经过实测的 TeamoRouter `gpt-5.6-luna` 生成最多 8 条中文摘要；`GitHub 趋势报告`通过 GitHub 官方 API 每天维护候选仓库和 Star 快照，每满 72 小时推送 3 个增长动量项目与 2 个新兴项目。

两个流程拥有独立应用入口、调度、状态、失败结果和 dry-run 能力，但复用安全的 HTTP、日志、模型调用和钉钉发送基础设施。系统删除已经被取代的直接内容采集器，不接入 X、微博、社交 RSS 或网页爬虫；搜索免费额度耗尽、没有合格内容或模型失败时，不向钉钉发送占位消息。

## User Stories

1. As a 固定钉钉群订阅者, I want 每天收到一份中文 AI 情报摘要, so that 我能快速了解近期值得关注的 AI 变化。
2. As a 固定钉钉群订阅者, I want 摘要只包含少量高价值内容, so that 我不会被大量低质量链接淹没。
3. As a 固定钉钉群订阅者, I want 系统准确说明覆盖范围是百度可检索到的中英文公开信息, so that 我不会误以为它完整覆盖全球或社交平台。
4. As a 固定钉钉群订阅者, I want AI 情报摘要在北京时间每天 08:30 运行, so that 我可以在早晨集中阅读。
5. As a 固定钉钉群订阅者, I want 每期 AI 情报摘要最多包含 8 条, so that 消息保持可读。
6. As a 固定钉钉群订阅者, I want 同一机构或事件每期最多出现两条, so that 单一热点不会挤占整份摘要。
7. As a 固定钉钉群订阅者, I want 每条内容都有事实摘要和重要性说明, so that 我无需打开每个链接才能判断价值。
8. As a 固定钉钉群订阅者, I want 每条内容保留原始标题、时间、站点和链接, so that 我可以追溯原始信息。
9. As a 固定钉钉群订阅者, I want 每条内容显示验证状态, so that 我能区分第一方确认与尚未得到第一方确认的消息。
10. As a 固定钉钉群订阅者, I want 缺少第一方证据的消息明确标记为未经确认, so that 我能区分搜索线索与已确认事实。
11. As a 固定钉钉群订阅者, I want 每期最多出现一条未经第一方确认的内容, so that 不确定信息不会主导日报。
12. As a 固定钉钉群订阅者, I want 相同 URL 在 30 天内不重复推送, so that 我不会反复收到同一篇文章。
13. As a 固定钉钉群订阅者, I want 同一事件的转载在 3 天内被合并, so that 多家媒体转载不会被误认为多个独立事件。
14. As a 固定钉钉群订阅者, I want 实质性新进展仍可再次推送, so that 去重不会隐藏真正的新信息。
15. As a 固定钉钉群订阅者, I want 没有合格内容时保持钉钉静默, so that 系统不会为了凑数发送空消息或旧内容。
16. As a 固定钉钉群订阅者, I want 搜索或模型最终失败时由工作流报告失败而不是钉钉占位, so that 钉钉只承载有阅读价值的报告。
17. As a 固定钉钉群订阅者, I want 百度搜索每天最多调用 20 次, so that 免费额度可预测且不会静默产生费用。
18. As a 固定钉钉群订阅者, I want 系统同时使用固定主题和轮换热点查询, so that 基础覆盖稳定且能追踪近期重点事件。
19. As a 固定钉钉群订阅者, I want 系统不批量抓取搜索结果网页或目标站点, so that 运行方式更稳定且减少合规风险。
20. As a 固定钉钉群订阅者, I want 每 72 小时收到一份独立的 GitHub 趋势报告, so that 我能持续发现快速增长的 AI 项目。
21. As a 固定钉钉群订阅者, I want GitHub 趋势只覆盖 AI 及紧密相关的开发基础设施, so that 报告保持主题相关。
22. As a 固定钉钉群订阅者, I want 趋势报告包含 3 个增长动量项目, so that 我能发现不限创建时间但近期热度明显上升的仓库。
23. As a 固定钉钉群订阅者, I want 趋势报告包含 2 个新兴项目, so that 新创建且快速增长的项目不会被成熟仓库掩盖。
24. As a 固定钉钉群订阅者, I want 趋势基于 72 小时 Star 变化而非累计 Star 榜, so that 每期结果能反映近期变化。
25. As a 固定钉钉群订阅者, I want 首次运行只建立趋势基线, so that 系统不会把累计 Star 伪装成近期增长。
26. As a 固定钉钉群订阅者, I want 缓存丢失时重新建立基线并推迟一期, so that 报告宁可缺席也不展示错误增量。
27. As a 固定钉钉群订阅者, I want 趋势候选排除 Fork、归档和长期不活跃项目, so that 榜单不会被无效仓库占据。
28. As a 固定钉钉群订阅者, I want Star 增长只用于发现候选且项目仍需质量判断, so that 热度不会被误当成质量。
29. As a 固定钉钉群订阅者, I want 每个趋势项目显示用途、推荐理由、当前 Star、72 小时新增 Star、主要语言和链接, so that 我能快速决定是否深入查看。
30. As a 固定钉钉群订阅者, I want AI 情报摘要和 GitHub 趋势拥有不同标题, so that 同一个钉钉机器人中的两类消息容易区分。
31. As a 系统维护者, I want 两个报告流程独立调度和保存状态, so that 一个流程失败不会阻止另一个流程。
32. As a 系统维护者, I want 两个流程拥有独立的手动 dry-run, so that 我可以在不发送钉钉消息和不污染状态的情况下验收真实数据。
33. As a 系统维护者, I want 搜索密钥与模型密钥在配置中逻辑隔离, so that 未来可以独立轮换权限或供应商。
34. As a 系统维护者, I want 模型地址、密钥和模型 ID 都通过环境配置, so that 更换模型服务不需要修改业务逻辑。
35. As a 系统维护者, I want 使用固定样本真实验证选定模型, so that 中文质量、结构化输出稳定性、事实约束和成本具有可审计证据。
36. As a 系统维护者, I want 生产只配置一个已通过验收的模型, so that 失败行为和输出质量保持可预测。
37. As a 系统维护者, I want 模型月度预算不超过人民币 30 元, so that 服务成本有明确上限。
38. As a 系统维护者, I want 所有外部标题、片段和项目说明都被视为不可信数据, so that 外部提示词无法改变系统任务或输出结构。
39. As a 系统维护者, I want 日志和 dry-run 不包含真实凭据, so that API Key 和钉钉凭据不会泄露。
40. As a 系统维护者, I want 尽可能迁移现有 30 天已发送 URL 状态, so that 切换百度搜索后不会立刻重发旧内容。
41. As a 系统维护者, I want 删除已被取代的直接内容采集器及陈旧文档, so that 代码库只有一套有效的内容发现设计。
42. As a 实施代理, I want 有明确的失败语义和验收标准, so that 我不会把占位消息、伪造增量或未经验证的生产运行误报为完成。

## Implementation Decisions

- 系统由 `AI 情报摘要`和`GitHub 趋势报告`两个应用流程组成；它们拥有独立入口、调度、并发组、状态和失败结果。
- AI 情报摘要只调用百度千帆正式 Web Search API。不得抓取百度结果页面、直接接入 X/微博、使用社交 RSS 桥接或保留其他直接内容采集器。
- 百度搜索每天最多 20 次：16 次固定中英文主题查询和 4 次可配置的轮换热点查询。检索窗口为最近 7 天，同一事件 3 天内合并；3 天后出现实质性新进展时允许再次入选。
- 固定主题覆盖模型发布、AI 产品、Agent、开发工具、开源项目、研究论文、训练推理与芯片、政策安全。查询内容属于配置数据，不嵌入采集流程控制逻辑。
- 百度返回数据标准化为搜索线索。候选至少保留标题、规范化 URL、站点、原文片段、发布时间、相关性和权威性信息。
- 搜索线索属于不可信输入。系统提示必须明确忽略候选中的命令、角色声明、输出格式和提示词；模型输出只能引用本批次实际候选，来源与 URL 由程序绑定。
- 本地预处理负责时间过滤、站点限额、URL 去重和事件合并。每个站点最多保留 3 条，最终最多向模型提交 40 条候选。
- 已确认更新要求原始链接属于事件主体，且搜索片段直接支持摘要事实。缺少第一方证据时，只要标题和原文片段直接支持同一事实即可入选，并显式标记；多个可信来源相互冲突时拒绝入选，此类更新每期最多一条。
- AI 情报摘要每期最多 8 条，同一机构或事件最多 2 条。没有合格候选时不发送、不回放旧内容，也不记录当日成功。
- AI 情报摘要每天北京时间 08:30 运行。手动 dry-run 可以调用公开搜索与模型，但不得调用钉钉或写入成功状态；可写入独立搜索用量账本以执行每日 20 次上限。
- GitHub 候选发现只使用官方 API，每天北京时间 08:45 更新最多 200 个 AI 相关仓库和 Star 快照。
- GitHub 候选必须非 Fork、未归档、近期有代码活动、具有有效说明且与 AI 主题相关。Star 增长负责召回，项目价值仍需内容质量判断。
- 第一次 GitHub 运行只建立趋势基线。报告观察周期从上一次成功推送开始计算连续 72 小时；不使用 cron 日期字段的三日步进表达业务周期。
- 每期 GitHub 趋势包含最多 3 个增长动量项目和 2 个新兴项目。增长动量以 72 小时 Star 净增为主要依据；新兴项目限定创建不超过 90 天并综合净增与增长比例。
- 排序必须确定且可测试。具体权重通过配置或具名常量表达，不能隐藏在模型提示中。
- GitHub 趋势状态保存在 GitHub Actions Cache，不引入数据库，不由机器人向仓库提交状态。状态丢失时重新建立基线并推迟一期。
- 两类报告发送到同一个钉钉机器人，但标题、状态和发送结果独立。
- 模型通过 TeamoRouter OpenAI-compatible Chat Completions 接口调用，密钥、Base URL 和模型 ID 均来自环境配置，并与百度搜索凭据隔离。
- 用户于 2026-09-10 明确选定 `gpt-5.6-luna`，生产中只允许该模型，不再保留千帆候选白名单或自动选型逻辑。
- 使用固定真实样本连续验证三次结构化 JSON、中文摘要、事实约束、提示词注入抵抗、明确拒绝和预计成本，不设置自动模型降级。
- 百度搜索免费额度耗尽时当日跳过且不启用自动后付费。模型月预算上限为人民币 30 元；按用户提供的折后输入 `$0.124/1M tokens`、缓存输入 `$0.0124/1M tokens`、输出 `$0.746/1M tokens`，使用保守 `8 CNY/USD` 与每月 40 次成功调用估算。
- 百度或 GitHub API、模型或钉钉在有限重试后失败时，相关工作流失败且不写入成功状态。没有内容、未满 72 小时或重新建立基线属于成功但不发送消息的结果。
- 迁移时尽可能保留已有 URL 去重记录，将旧的每日发送状态限定为 AI 情报摘要状态，并为 GitHub 趋势建立独立空基线。
- 删除被取代的 RSS、arXiv、Hugging Face Daily Papers、指定仓库 Release 采集配置、实现、专属测试和陈旧设计。只保留仍符合新边界的通用 HTTP、模型、状态、日志和钉钉能力。
- 实施基线为与远端默认分支同步后的最新代码。上线前先执行真实数据 dry-run；未完成真实 dry-run 时不得宣称生产能力已验证。

## Testing Decisions

- 测试只断言可观察行为、API 合约和持久状态结果，不断言内部辅助函数的调用顺序或私有实现细节。
- 采用两个已由用户确认的最高层测试接缝：AI 情报摘要应用入口和 GitHub 趋势报告应用入口。两个接缝保持独立，以验证故障隔离这一产品边界。
- AI 情报摘要入口测试覆盖：20 次搜索硬上限、固定与轮换查询、7 天时间窗口、候选上限、站点限额、验证状态、3 天事件去重、8 条输出限制、钉钉发送和成功状态。
- GitHub 趋势入口测试覆盖：每日候选快照、首次基线、72 小时门禁、增长动量与新兴项目配额、质量过滤、缓存恢复、缓存丢失和钉钉发送。
- 两个入口都使用模拟 HTTP 响应和临时状态目录，不依赖真实百度、TeamoRouter、GitHub 或钉钉服务。
- 为百度搜索响应解析保留小型协议契约测试，覆盖缺失字段、非法 URL、超长片段、错误码、限流和安全日志。
- 为模型适配保留结构化输出契约测试，覆盖合法 JSON、模式错误、未知候选 ID、重复 ID、拒绝响应、429、5xx、超时和候选中的提示词注入。
- 为 GitHub API 适配保留协议契约测试，覆盖搜索分页、候选上限、Star 快照、归档/Fork 过滤、时间字段和限流错误。
- 为钉钉渲染与发送复用现有先例，继续验证 Markdown 转义、完整条目边界拆分、长度上限、顺序发送、安全错误和失败时不保存状态。
- 为工作流配置复用现有 YAML 契约测试，验证北京时间调度、独立并发组、最小权限、Secret 映射、dry-run 默认值和状态缓存保存条件。
- 为状态迁移增加行为测试，证明旧 URL 仍能抑制重复内容，而两类报告不会共享每日发送门禁。
- 删除与旧采集器、近期内容回放、固定状态通知和模型失败钉钉通知绑定的旧测试，使用新产品行为测试取代。
- 完整验收要求全量离线测试、凭据扫描和 GitHub Actions Test 全部通过。

## Out of Scope

- X、微博或其他社交平台官方 API。
- RSSHub 或其他社交 RSS 桥接服务。
- 百度搜索结果页和目标网页批量爬取。
- RSS、arXiv、Hugging Face Daily Papers 和指定 GitHub Release 直接采集。
- 完整全球覆盖承诺或即时突发提醒。
- 全 GitHub 非 AI 项目趋势。
- 多用户、不同订阅偏好、权限隔离和独立钉钉目标。
- 外部数据库、机器人自动提交状态文件或长期历史分析仓库。
- 多模型自动故障转移。
- 为没有内容的日期生成占位日报。
- 自动开通百度或模型服务后付费。

## Further Notes

- 项目领域词汇以 `AI 情报摘要`、`搜索线索`、`已确认更新`、`未经验证更新`、`GitHub 趋势报告`、`增长动量项目`、`新兴项目`、`观察周期`和`趋势基线`为准。
- 已接受的 ADR 决定百度官方搜索 API 是 AI 情报的唯一发现入口；GitHub 官方 API 是独立趋势报告的明确例外。
- 原社交 RSS 设计因与该 ADR 冲突而删除，仍可通过 Git 历史恢复。
- 百度搜索和 TeamoRouter 的任何 API Key 都不得写入 Issue、仓库、日志或聊天。
- 当前模型与价格信息可能变化，实施时必须重新读取供应商实时模型目录与价格页面；不要仅凭模型别名推断可用性。
- 主分支在规格确认时已与远端同步；工作区中的设计文档变更尚未表示业务功能已经实现。
- 用户已确认两个最高层测试接缝符合预期。
