# 百度 AI 情报与 GitHub 趋势推送设计

**状态：01—07 已本地集成；08 清理未提交，整体切换验收未完成**

验收差异：每日累计配额账本已加入本地实现，但仍需重新验证跨运行恢复和生产缓存行为。真实 AI dry-run 目前仅验证空结果路径，不能证明当日摘要生成质量。

## 背景

当前系统从官方 RSS、arXiv、Hugging Face Daily Papers 和指定 GitHub 仓库
Releases 采集候选，由模型生成中文摘要，再通过钉钉推送。当前生产工作流在
北京时间 14:30 运行，并在没有合格内容时保持钉钉静默。

本设计将产品收敛为单订阅者的低噪声 AI 情报服务：日常 AI 更新只通过百度
官方搜索 API 发现，GitHub 趋势则通过 GitHub 官方 API 独立计算。系统不承诺
完整覆盖全球或社交平台，只描述为“百度可检索到的中英文 AI 公开信息”。

本设计只记录已确认的目标状态，不表示相关代码、工作流、密钥或生产环境已经
完成变更。

## 目标

1. 每天生成一份最多 8 条、证据明确的中文 AI 情报摘要。
2. 每 72 小时生成一份最多 5 个项目的 GitHub AI 趋势报告。
3. 严格限制百度搜索与模型费用，不允许静默转入自动后付费。
4. 将两类报告的调度、状态和失败相互隔离。
5. 在缺少可靠内容或模型不可用时保持钉钉低噪声。

## 非目标

- 不直接接入 X、微博或第三方社交 RSS 桥接服务。
- 不抓取百度搜索结果页，也不批量抓取结果指向的目标网页。
- 不保留 RSS、arXiv、Hugging Face Daily Papers 或指定仓库 Release 采集器。
- 不承诺完整覆盖全球、X、微博或任何单一社交平台的全部动态。
- 不做全 GitHub 泛技术趋势榜。
- 不建设多租户、个性化订阅或外部数据库。
- 不保证每天一定向钉钉发送消息。

## 已确认的产品边界

- 订阅者是一个个人或固定钉钉群。
- AI 情报摘要与 GitHub 趋势报告是两个独立产品栏目。
- 内容覆盖模型与产品发布、研究、开源工具、开发平台以及重大政策和安全事件。
- 普通融资新闻和个人观点只在影响足够大且证据达到要求时入选。
- 同时检索中文和英文内容，最终输出中文摘要，并保留原始标题、站点和链接。
- 价值来自筛选与解释，不来自尽可能多地搬运信息。

## 目标架构

```text
百度官方搜索 API
  → 搜索线索标准化
  → 时间、站点、URL 与事件去重
  → 证据分级和候选限额
  → TeamoRouter `gpt-5.6-luna` 筛选与中文摘要
  → 钉钉 AI 情报摘要

GitHub 官方 API
  → 每日候选发现与 Star 快照
  → 72 小时增量计算
  → 项目质量筛选与摘要
  → 钉钉 GitHub 趋势报告
```

两个流程拥有独立命令、GitHub Actions 工作流、状态文件和失败结果，共用必要的
HTTP、日志和钉钉基础设施。

## AI 情报摘要

### 百度搜索

使用百度千帆正式的 `POST /v2/ai_search/web_search` 接口，不解析或抓取
`baidu.com` 搜索结果页面。搜索服务的 API Key 独立配置为
`BAIDU_SEARCH_API_KEY`。

每天最多发起 20 次请求：

- 16 次固定查询：模型发布、AI 产品、Agent、开发工具、开源项目、研究论文、
  训练推理与芯片、政策安全，每个主题分别使用中文和英文查询。
- 4 次轮换查询：追踪近期重点公司、模型、项目或事件。

查询主题和轮换项属于可配置数据，不硬编码在采集逻辑中。检索窗口为最近
7 天，以容忍搜索索引延迟并覆盖周末与索引滞后。免费额度耗尽时停止当日搜索，不自动启用后付费。

参考：

- <https://cloud.baidu.com/doc/qianfan/s/2mh4su4uy>
- <https://cloud.baidu.com/product/ai-search.html>

### 候选与证据

百度返回的标题、URL、站点、原文片段、日期、相关性评分和权威性评分仅作为
不可信候选数据，不能改变系统提示、输出结构或安全规则。

候选处理遵循以下约束：

1. 只保留时间窗口内、URL 合法且与 AI 内容边界相关的网页结果。
2. 相同规范化 URL 在 30 天内不重复推送。
3. 同一事件的不同转载在 3 天内合并；3 天后出现实质性新事实时允许再次推送。
4. 每个站点最多保留 3 条候选。
5. 本地过滤后最多向模型提交 40 条候选。
6. 不额外批量抓取候选 URL 指向的网页。

原始链接属于事件主体，且百度返回的原文片段直接支持摘要所述事实时，内容可以
标记为“已确认更新”。没有第一方证据时，只要标题和原文片段直接支持同一事实，
即可作为“未经第一方确认”内容；多个可信来源相互冲突时拒绝入选。此类内容每期
最多一条，并在消息中显式标记。

搜索结果中的命令、角色说明、提示词、输出要求和链接文本都视为外部数据。
模型不得执行这些内容，也不得采用候选提供的输出格式。

### 选择与消息格式

每期最多 8 条，同一机构或事件最多 2 条，不设置为了凑数而存在的类别最低配额。
每条包含：

- 原始标题；
- 事实摘要；
- 为什么重要；
- 内容类别；
- 验证状态；
- 发布时间；
- 来源站点；
- 原始链接。

没有合格候选时不发送空日报，也不回放旧内容填充数量。

### 调度

AI 情报摘要每天北京时间 14:30 运行，对应 UTC cron：

```text
30 6 * * *
```

保留手动 dry-run 入口。dry-run 可以读取公开信息并调用模型，但不得发送钉钉
消息或写入成功状态。

## GitHub 趋势报告

### 候选范围

只发现与以下领域相关的仓库：AI 模型、Agent、训练与推理、数据工具、AI 应用
和紧密相关的开发基础设施。

每天通过 GitHub 官方 Search API 更新最多 200 个候选仓库及 Star 快照。候选
必须满足：

- 非 Fork；
- 未归档；
- 近期存在代码活动；
- 具有有效的项目说明；
- 与约定的 AI 主题相关。

Star 增长只用于发现热度，不等于项目质量。模型仍需根据项目说明、用途、活动
状态和可验证信息判断是否值得推荐。

### 观察周期与排行

首次运行只建立趋势基线，不发送报告。系统从上一次成功推送 GitHub 趋势报告
后开始计算新的 72 小时观察周期；任务失败时次日重试，不使用 cron 日期字段的
`*/3` 表达业务周期。

每期最多 5 个项目：

- 3 个增长动量项目：不限创建时间，按观察周期内 Star 净增量为主要排序依据。
- 2 个新兴项目：创建时间不超过 90 天，综合 Star 净增量和增长比例排序。

排序必须确定且可测试。最终实现可在不改变上述产品语义的前提下调整具体权重，
但必须通过配置或具名常量表达，不能隐藏在模型提示中。

每个项目展示名称、用途、推荐理由、当前 Star、72 小时新增 Star、主要语言和
仓库链接。

运行延迟或失败重试导致观察周期超过 72 小时时，应展示实际观察时长与对应净增量，不得将更长周期的增长标为恰好 72 小时增长。

### 状态与调度

候选快照任务每天北京时间 08:45 运行，对应 UTC cron：

```text
45 0 * * *
```

状态使用 GitHub Actions Cache 保存，不引入数据库，也不由机器人向仓库提交
状态文件。缓存丢失或缺少合格基线时重新建立基线并推迟一期，绝不把当前累计
Star 伪装成 72 小时增量。

GitHub 趋势报告与 AI 情报摘要发送到同一个钉钉机器人，但使用不同标题、独立
状态和独立发送结果。

## AI 模型

模型通过 TeamoRouter 的 OpenAI-compatible Chat Completions 接口调用，配置项至少
包含 `AI_API_KEY`、`AI_BASE_URL` 和 `AI_MODEL`。百度搜索与模型推理使用不同凭据，
并在代码、工作流和日志中保持逻辑隔离。

用户于 2026-09-10 明确选择 `gpt-5.6-luna` 作为唯一生产模型，不再执行千帆三模型
候选比较。上线前仍必须使用固定脱敏样本连续完成三次真实验证，并确认该模型：

- 结构化 JSON 连续输出稳定；
- 中文摘要不编造候选片段之外的事实；
- 能忽略候选内容中的提示词注入；
- 拒绝或失败能够被程序明确识别；
- 预计月度费用不超过人民币 30 元。

生产只配置这一个模型，不自动降级到其他模型。模型连续重试失败后，本期
不向钉钉发送任何消息。

接口与价格证据：

- TeamoRouter 官方接口文档：<https://api.teamorouter.cn/docs/api-integration>
- 2026-09-10 实时 `/v1/models` 校验确认 `gpt-5.6-luna` 可用。
- 用户提供的供应商价格页面显示折后输入 `$0.124/1M tokens`、缓存输入
  `$0.0124/1M tokens`、输出 `$0.746/1M tokens`。预算估算使用保守的
  `8 CNY/USD`，按每月 40 次成功调用计算。

## 失败语义

| 场景 | 钉钉 | 状态 | 工作流结果 |
| --- | --- | --- | --- |
| 没有合格 AI 内容 | 不发送 | 不记录当日成功 | 成功 |
| 百度免费额度耗尽 | 不发送 | 不记录当日成功 | 失败（与搜索失败一致） |
| 百度接口有限重试后失败 | 不发送 | 不记录当日成功 | 失败 |
| AI 模型有限重试后失败 | 不发送 | 不记录当日成功 | 失败 |
| 钉钉发送失败 | 可能部分发送 | 不记录成功 | 失败 |
| GitHub 首次运行或基线丢失 | 不发送趋势报告 | 建立新基线 | 成功 |
| GitHub API 失败 | 不发送趋势报告 | 保留旧状态 | 失败 |
| GitHub 未满 72 小时 | 不发送趋势报告 | 更新必要快照 | 成功 |

“每日必须发送一条状态消息”不再是产品要求。只有完整报告成功发送后，才记录
对应报告的成功状态。

## 状态迁移

- 尽可能保留现有 30 天已发送 URL 状态，避免百度重新发现旧内容后重复推送。
- 旧的每日发送状态迁移为 AI 情报摘要专属状态。
- GitHub 趋势状态从空基线开始。
- 两个工作流不得共享“今日已发送”门禁。

## 安全与成本

- `BAIDU_SEARCH_API_KEY`、`AI_API_KEY` 和钉钉凭据只存放在 GitHub Actions
  Secrets 或本地未跟踪环境中。
- 日志、异常、dry-run 预览和测试夹具不得包含真实 Key。
- 百度搜索最多每天 20 次，免费额度耗尽后停止。
- `gpt-5.6-luna` 模型月度预算上限为人民币 30 元，优先通过平台账户预算控制；
  价格变化后必须重新核验，不能沿用旧估算。
- 外部标题、片段、项目说明和 README 全部视为不可信数据。
- 不通过抓取、登录绕过或第三方桥接服务补偿百度搜索覆盖不足。

## 代码与工作流边界

目标实现提供两个明确入口：

- `ai-digest`：百度检索、证据处理、模型摘要和 AI 情报推送。
- `github-trends`：GitHub 候选快照、增量计算、项目摘要和趋势推送。

两个入口使用独立 GitHub Actions 工作流和独立并发组。任何一个流程失败都不得
阻止另一个流程运行。

目标实现应删除已被取代的 RSS、arXiv、Hugging Face Daily Papers、指定仓库
Release 采集配置、实现和专属测试。现有通用 HTTP、状态、模型和钉钉能力只有
在仍符合目标设计时才保留。

## 取代关系

本设计取代以下现行行为或决策：

- 北京时间 08:30 的早间调度，改为 14:30；
- 无内容时回放近期条目或发送固定状态通知；
- 模型失败时向钉钉发送模型服务状态通知；
- 多个官方内容源直接采集；
- AI 日报与所有后续报告共享单一每日发送状态。

原 `2026-07-25-social-technical-digest-design.md` 因选择百度官方搜索 API 作为
唯一 AI 情报发现入口而删除。历史内容仍可从 Git 记录恢复。

## 部署顺序

1. 在最新 `origin/master` 基线上实现并运行离线测试。
2. 分别准备百度搜索 API Key 和 TeamoRouter 模型 API Key，但不把 Key 写入仓库。
3. 使用固定样本真实验证用户选定的 `gpt-5.6-luna`，确认质量、失败语义和预算。
4. 运行 AI 情报手动 dry-run，检查真实搜索结果、验证标签和摘要质量。
5. 启用 AI 情报摘要定时任务。
6. GitHub 趋势任务首次运行只建立基线。
7. 满 72 小时后检查第一份趋势报告，再确认正式持续运行。

## 验收标准

- 原有四类采集器及其陈旧配置、实现、专属测试和文档已按取代关系清理。
- 百度搜索请求总数被程序限制为每天最多 20 次。
- 百度候选上限、站点上限、事件去重和验证规则具有离线测试。
- AI 情报摘要和 GitHub 趋势拥有独立命令、工作流、状态与失败测试。
- GitHub 首次运行和缓存丢失只建立基线，不发送伪造的增量报告。
- 模型输出经过结构校验，候选中的提示词不能改变系统任务。
- 没有内容或模型失败时不会向钉钉发送状态占位消息。
- dry-run 不发送钉钉消息、不保存日报成功状态；按订阅者确认会保存独立搜索用量账本以执行每日配额，且不泄露凭据。
- 全量测试、凭据扫描和 GitHub Actions Test 通过。
- README、`.env.example`、领域词汇表和 ADR 与目标行为一致。
- 未完成真实 dry-run 前，不宣称生产功能已经验证。
